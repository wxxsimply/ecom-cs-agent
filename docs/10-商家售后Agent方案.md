## 0. 结论先行

**产品方向**：从“面向消费者的问答客服”转向 **面向商家的售后判责与编排 Copilot**（与 08 的 D1 决策一致）：

> 商家售后人员把买家工单交给 Agent；Agent 负责理解、查证、判责、给出动作建议/草稿与证据卡；低风险动作可由商家确认后执行，涉及钱、权限、例外、投诉的由商家内部审核；执行调用 ERP 售后接口，不自造执行引擎。

**核心设计**：

1. 不是“AI 替代商家”，而是 **AI 承担售后判责与编排，商家保留审批与责任**。
2. 75 条 `tickets_v1` 中标注“人工=是”的 20 条，解读为 **merchant review（商家内部审核/接管）**，不是“把买家转给人工客服”。
3. 钱/资格/金额/权限由确定性规则计算；LLM 只负责理解、解释、草稿和流程编排。
4. Agent 输出统一动作：`answer / query / clarify / refund_apply / refund_reject / exchange_apply / cancel_order / review / assign_human`。
5. 先做 **Copilot + 审批门**；执行动作通过 ERP adapter，不做“全自动退款”。
6. 08 的定位仍是**求职作品优先**：先用 75 条工单 + 3–5 位从业者访谈 + 真实模型验证；商业试用是后续选项，不是默认。

### 0.1 市面上客服 Agent 的“毒点”与本项目切口

> “毒点”不是“竞品完全没有”，而是**在自营商城 + 自有 ERP + 售后判责场景下，现有产品的默认设计解决不好**。公开证据见 08/09；未找到证据的地方标“待验证”，不当作竞品没有。

| # | 市场毒点 | 现有产品为什么容易卡住 | 本项目的解法 | 可证伪指标 |
| --- | --- | --- | --- | --- |
| P1 | 只会答，不会判 | 平台机器人强在问答/导购；判责依赖商家规则与订单事实 | **判责核心**：订单事实 + 政策 + 金额 + 风险，输出 action proposal | 退款/资格/金额错误 = 0 |
| P2 | 规则散、过期、不可解释 | 规则在后台/Excel/人脑；大促一变就错 | 政策快照 + 规则版本 + 证据卡；回答引用条款 | 证据可定位 ≥95%；过期规则 0 |
| P3 | 跨系统（千牛/聚水潭/钉钉） | 聊天、ERP、物流各一套；AI 只看到聊天 | 工单上下文聚合 + ERP adapter；不替代 ERP | 一张工单所需事实一次拉齐 |
| P4 | 转人工/审批割裂 | AI 到“转人工”就结束；审批在群里/线下 | 商家内部审批门；proposal → approve → execute | 高风险 100% 有审批 |
| P5 | 金额/对账靠人 | 退款金额、运费、积分分摊容易错 | 服务端确定性计算 + breakdown + 对账事件 | false approve = 0；金额误差 0 |
| P6 | 例外处理（部分退/少件/错发/签收争议） | 通用 bot 只会标准流程，遇到例外就拒/转 | 例外 playbook + 人工复核 + 证据清单 | 例外样本不误判；reject 有依据 |
| P7 | 不可追溯/不可申诉 | 用户不知道为什么被拒；商家无法复盘 | 每次动作留证据/规则版本/审批人；拒绝给依据/申诉 | 审计完整 100% |
| P8 | 执行不可逆 | 直接调用退款，失败/重复/越权 | 幂等键 + 审批 + 执行前重算 + 回滚 | 重复执行 0；对账差异可解释 |
| P9 | 评价自证 | 厂商宣称“解决率 80%”，合成集/自造集 | 75 条 dev/holdout + 真实工单 + 代价矩阵 | 报告区分合成/真实 |
| P10 | 私有化/数据安全 | SaaS 接入深，商家数据出域 | 单商家可私有化；最小权限；PII 脱敏 | 数据不出域可验证 |
| P11 | 只看“转人工率” | 把转人工当唯一 KPI，忽略误退/返工 | 看 false approve、返工、CSAT、处理分钟、纠纷 | 不以转人工率单独验收 |
| P12 | 责任边界模糊 | AI 口头承诺退款/时效，出事无人负责 | AI 只建议；人审批；动作可回滚；责任链留痕 | 审批人/执行人可追溯 |

**一句话切口**：

> 不做“更会聊天的客服”，做 **自营商城售后判责与编排层**：把“该不该退/退多少/依据哪条/证据够不够/异常怎么办/谁批准/执行到哪”做成可审计的 action，而不是再做一个聊天框。

### 0.2 这个切口不解决什么

- 不替代 ERP 的售后执行引擎；
- 不做平台站内全渠道客服；
- 不做售前导购/通用问答；
- 不做无审批的全自动退款；
- 不承诺“所有商家都适用”；先验证鞋服/眼镜等退换高频、规则清晰的垂直。

## 1. 需求澄清

### 1.1 用户与角色

| 角色 | 要解决的问题 | 关键诉求 |
| --- | --- | --- |
| 商家老板/售后负责人 | 售后成本高、口径不统一、出错不可追溯 | 省时、少错、可审计、可汇报 |
| 售后客服 | 每天大量重复查询、判责、写回复 | 少切系统、有依据、可一键采用 |
| 客服主管 | 审批、质检、培训 | 风险分级、审批记录、复盘 |
| 买家（间接） | 问题被解决、不被踢皮球 | 快、准确、有人负责 |

### 1.2 要做的 Job

1. **接入**：把买家消息/工单变成结构化售后单。
2. **理解**：识别意图、订单、商品、原因、情绪、紧急度。
3. **查证**：订单、物流、退款、政策、商品、历史工单。
4. **判责**：是否可退/可换/可取消、金额、运费、时限。
5. **建议/执行**：给出动作 + 回复草稿；低风险自动，高风险审批。
6. **回复**：按品牌语气解释依据、金额、下一步。
7. **留痕**：证据、规则版本、审批人、执行结果。
8. **学习**：人工修改/拒绝/投诉回流评测与知识。

### 1.3 关键术语：两种“人工”必须分开

| 术语 | 定义 | 本方案 |
| --- | --- | --- |
| 消费者转人工 | 买家从 AI 转到人工客服队列 | **非紧急不做**；紧急才实时 |
| 商家内部审核 | 商家员工/主管审批 Agent 的建议 | **必须保留**，是责任边界，不是客服转接 |
| 人工接管工单 | 复杂工单分配给商家售后人员 | 允许，但 Agent 先完成查证/草稿 |

> 因此，`tickets_v1` 的 `人工=是` 不应被理解为“AI 无法回答”，而是“该动作需要商家审批/接管”。这是本方案与上一版“非紧急不转人工”的调和点。

### 1.4 目标与非目标

> 08 已把本项目定位为**求职作品优先**：P1 先证明“售后判责与编排”的工程能力，商业试用是后续选项。因此本方案同时服务两件事：可讲清楚的差异化 + 可被商家验证的产品假设。

**目标**：

- 75 条工单的 action/金额/审核路由可评测，形成可复现证据。
- 退款资格/金额错误 **0**。
- 高风险动作 100% 有审批与审计。
- 若进入商家试用：售后单处理时间下降 ≥30%（真实商家验证，不用合成数据自证）。

**非目标（本轮）**：

- 不做真实 OMS/支付/物流写入；先做 adapter 契约。
- 不做多商家 SaaS、多租户计费。
- 不做全自动退款打款。
- 不做消费者端全量替代。
- 不把合成工单当真实市场证据。

### 1.5 功能需求（P1）

| ID | 需求 | 优先级 | 说明 |
| --- | --- | --- | --- |
| FR-01 | 工单接入与归一化 | P0 | 买家消息 → `AfterSalesTicket`；渠道/买家/订单/时间统一 |
| FR-02 | 身份与权限 | P0 | 买家/客服/主管/老板角色；买家只能看自己；审批权限分离 |
| FR-03 | 上下文聚合 | P0 | 订单、商品、物流、退款、历史工单一次拉齐；只读优先 |
| FR-04 | 意图/动作/槽位 | P0 | 13 类意图 + 9 类 action；缺失槽位只问一个 |
| FR-05 | 政策检索与证据 | P0 | 政策/商品/FAQ 命中；引用可定位；规则版本快照 |
| FR-06 | 确定性判责 | P0 | 资格、金额、运费、时限、风险；服务端计算，不让 LLM 算 |
| FR-07 | 动作建议与回复草稿 | P0 | action proposal + amount breakdown + 证据卡 + 草稿 |
| FR-08 | 审批门 | P0 | auto/review/assign/emergency；高风险必审 |
| FR-09 | ERP 执行 adapter | P0/P1 | 调用 ERP 售后接口或 CSV/自建 API；不自造执行引擎 |
| FR-10 | 回复与状态同步 | P0 | 买家回复、工单状态、退款/换货/取消结果 |
| FR-11 | 审计与对账 | P0 | proposal→approval→execute 全链路；幂等键；差异告警 |
| FR-12 | 例外 playbook | P0 | 高金额、特殊品类、签收争议、部分退、投诉、改地址 |
| FR-13 | 评测与回流 | P0 | 75 条 dev/holdout；人工修改/拒绝/投诉回流 |
| FR-14 | 可观测 | P1 | trace、action/amount/审批耗时、失败原因 |

### 1.6 非功能需求

| ID | 需求 | 标准 |
| --- | --- | --- |
| NFR-01 | 金额/资格正确性 | 退款/驳回金额、资格错误 = 0；错一单即阻断 |
| NFR-02 | 权限与隐私 | 买家/商家/审批人隔离；PII 脱敏；越权 = 0 |
| NFR-03 | 幂等 | 同一 ticket+action+policy+amount 重复请求不重复执行 |
| NFR-04 | 可追溯 | 每单有证据、规则版本、审批人、执行结果 |
| NFR-05 | 延迟 | 查询/判责 P95 ≤ 3s；执行受 ERP 限制，单独记录 |
| NFR-06 | 可用性 | P1 单实例可接受；故障时只读/排队，不丢工单 |
| NFR-07 | 数据边界 | 支持单商家私有化；真实工单不提交仓库 |
| NFR-08 | 合规 | AI 身份、审批责任、拒绝理由、申诉路径可解释 |

### 1.7 P1 范围（冻结）

**In Scope**：

- 1 个自营商城商家 + 1 个垂直（鞋服或眼镜）；
- 3 个售后动作：退款、退货、换货；
- `cancel_order` 只做状态判断/建议/审核，不做已支付/已发货自动取消；
- 查询/回答/澄清 + 低风险动作建议 + 商家审批；
- 1 个 ERP adapter（聚水潭/自建 API/CSV 三选一，先 mock/CSV）；
- 工单列表/详情/证据卡/审批/审计最小工作台；
- 75 条 tickets 评测；真实模型对比；
- 3–5 位从业者访谈（作品验证，不宣称商业效果）。

**Out of Scope**：

- 全自动退款/打款、自动改地址、部分退自动执行；
- 已支付/已发货订单的自动取消；
- 多商家 SaaS、多租户计费、完整运营台；
- 平台站内全渠道客服、售前导购；
- 自研 ERP 执行引擎；
- 真实支付/物流写操作（P1 只做 adapter 契约与 sandbox）；
- 无审批的高风险执行。

## 2. 数据证据：tickets_v1 告诉我们什么

### 2.1 数据概况

- 共 **75 条**：`dev` 50、`holdout` 25。
- 全部为合成数据，期望值由 `app/refunds.py` 和 `data/knowledge/*.md` 推导。
- 标注列：ID、消息、订单、意图、动作、金额、人工、依据。

| 维度 | 分布 |
| --- | --- |
| 意图 | refund_request 22、policy_qa 16、order_query 6、product_qa 5、general_qa 5、logistics_query 4、needs_clarify 3、after_sales 3、out_of_scope 3、complaint 2、human_request 2、emergency 2、chitchat 2 |
| 动作 | answer 31、refund_apply 15、handoff 10、refund_reject 6、query_order 4、clarify 4、query_logistics 3、cancel_order 1、exchange_apply 1 |
| 人工=是 | 20/75（26.7%） |

### 2.2 20 条“人工=是”的真实含义

| 类型 | 例子 | 应映射为 |
| --- | --- | --- |
| 高金额/特殊品类退款 | 1004 显示器 699、1007 定制品、1010 手机、1011 羽绒服 | `review_required`（金额/品类风险） |
| 已发货/少件/错发 | 1003 发错货、1004 少发配件、1011 已发货 | `review_required`（物流/责任） |
| 签收争议 | 1006 显示签收但未收到 | 商家审核 + 物流理赔 |
| 投诉/情绪 | 1006 客服态度差、1004 再不处理就投诉 | 主管审核/接管 |
| 明确要人工 | “转人工”“我要人工客服” | 分配给商家售后人员 |
| 紧急 | 被骗、账号被盗 | 紧急处理 |
| 改地址 | 1001 改地址 | 运营审核 |
| 规则不确定 | 退款多久到账 | 先查知识；仍不确定则审核 |

**结论**：20 条不是“AI 答不了”，而是“这件事需要人承担责任/权限”。Agent 应把“建议 + 证据 + 风险”准备好，减少审核时间，而不是把整单丢给人。

### 2.3 当前实现差距

| 能力 | tickets_v1 期望 | 当前实现 | 差距 |
| --- | --- | --- | --- |
| 工单对象 | 75 条 ticket | 只有 session/message/refund/ticket 雏形 | 缺 `AfterSalesTicket` 主对象 |
| 动作 | answer/query/refund/exchange/cancel/review | 只有 answer/query/refund/handoff | 缺 exchange/cancel/review 动作 |
| 金额 | 15 条 apply 金额 | 退款金额已服务端算 | 缺 action proposal/金额快照 |
| 人工 | 20 条需审核 | 按规则 `requires_human` 散落 | 缺风险分级/审批模型 |
| 评测 | 75 条 action/金额/人工 | 只有 50 条 answer-first | 缺 ticket eval runner |
| 商家视角 | 商家审核/接管 | 消费者对话 | 缺工作台/角色/审批 |

### 2.4 工单中最像“毒点”的 10 个簇

| 簇 | 代表工单 | 为什么毒 | 方案必须给什么 |
| --- | --- | --- | --- |
| 高金额退款 | T-036/T-037/T-046/T-047/T-048 | 金额大、审批链长；错一单不可逆 | 金额 breakdown + 风险门 + 主管审批 |
| 特殊品类 | T-043/T-044/T-052/T-053 | 定制品/少件/错发，规则例外 | 例外 playbook + 证据卡 + 拒绝依据 |
| 签收争议 | T-033 | 显示签收但买家说没收到 | 物流轨迹 + 签收人 + 理赔/复核 |
| 部分退 | T-057 | 当前只支持整单退 | 明确“暂不支持自动部分退”，给人工/工单，不编金额 |
| 退款时效 | T-056 | 知识不确定，容易编“马上到” | 查政策；不确定则审核，不承诺具体到账 |
| 投诉/情绪 | T-061/T-062 | 通用 bot 直接转人工或只会道歉 | 共情 + 事实 + 补救 + 主管审核 |
| 改地址 | T-069 | 已支付/已发货状态限制 | 状态判断 + 运营审核 + 不口头承诺 |
| 取消订单 | T-031 | 未支付可自助，已支付需拦截 | 状态路由 + 审批 + ERP 调用 |
| 换货 | T-040 | 换码/换货不是退款 | exchange_apply + 库存/物流校验 |
| 越权/隐私 | T-067/T-068 | 查他人订单/要老板电话 | 拒绝 + 合规替代 + 审计 |

**关键结论**：`tickets_v1` 的 20 条 human 不是“答不出”，而是这些簇需要**判责、证据、审批、执行**。如果 Agent 只优化回答文本，就会在这 10 个簇上被“毒”到。

## 3. 产品形态

### 3.1 三种模式

| 模式 | 说明 | 建议 |
| --- | --- | --- |
| A. Copilot | Agent 查证/判责/写草稿，商家确认后发送；执行通过 ERP adapter | **先做** |
| B. 低风险自动 | answer/query/clarify 自动；refund/exchange/cancel 仍需审批；ERP 调用需幂等/对账 | P1 |
| C. 全自动 | 自动退款/打款/改地址 | 暂不做，需真实 OMS + 风控 + 审计 |

### 3.2 界面

1. **售后工作台**：工单列表（待处理/待审核/已处理/异常）、优先级、SLA、风险标签。
2. **工单详情**：买家原话、订单/物流、证据、政策版本、Agent 建议、金额 breakdown、回复草稿。
3. **审批卡**：通过/修改/拒绝，必须填原因；高风险双人复核。
4. **审计时间线**：谁在何时改了什么、执行结果、幂等键。
5. **买家侧**：只看到最终回复/动作结果，不暴露内部审核。

### 3.3 角色权限

| 角色 | 权限 |
| --- | --- |
| `merchant_agent` | 查看/处理低风险；提交退款建议；不能审批自己提交的高风险 |
| `merchant_supervisor` | 审批退款/换货/例外；接管投诉 |
| `merchant_owner` | 配置政策/额度/权限；查看报表 |
| `system_agent` | 查证、草稿、低风险执行；不可改金额/权限 |

## 4. 售后 Agent 的动作设计

### 4.1 动作清单

| action | 含义 | 默认自动化 | 审批 |
| --- | --- | --- | --- |
| `answer` | 政策/商品/一般问题回答 | 自动 | 无 |
| `query_order` | 查订单状态 | 自动 | 无 |
| `query_logistics` | 查物流/轨迹 | 自动 | 无 |
| `clarify` | 缺槽位，问一个问题 | 自动 | 无 |
| `refund_apply` | 创建退款申请 | 条件自动 | 高风险需审批 |
| `refund_reject` | 拒绝退款并解释 | 条件自动 | 例外/高金额需审批 |
| `exchange_apply` | 换货申请 | 条件自动 | 高价值/特殊品类需审批 |
| `cancel_order` | 取消未支付/未发货订单 | 条件自动 | 已支付/已发货需审批 |
| `review` | 转商家内部审核 | 自动路由 | 人工决策 |
| `assign_human` | 分配给售后人员/主管 | 自动路由 | 人工接管 |
| `emergency` | 安全/诈骗/紧急 | 立即标记 | 紧急人工 |
| `out_of_scope` | 非售后范围 | Answer-first 边界回复 | 无 |

**执行层边界**：本项目不自造退款/换货执行引擎；审批通过后通过 `ErpAfterSalesAdapter` 调用 ERP（如聚水潭售后上传/收货接口）或商家自建 API。Adapter 负责幂等键、请求/响应留痕、对账差异；Agent 只产出 proposal 和参数，不直接打款。

### 4.2 决策顺序

```text
1. 安全/紧急？
2. 是否售后范围？
3. 订单/商品/物流是否可定位？
4. 政策是否命中？证据是否足够？
5. 动作是否可自动？金额/权限是否在额度内？
6. 生成 action proposal + 回复草稿
7. 风险门：auto / review / assign / emergency
8. 执行（幂等）或等待审批
9. 回复 + 审计 + 回流
```

### 4.3 风险分级（建议初始值）

| 风险 | 条件 | 处理 |
| --- | --- | --- |
| R0 | answer/query/clarify | 自动 |
| R1 | 退款 ≤ 200、已支付未发货、规则明确 | 自动建议 + 抽样审核 |
| R2 | 退款 200–500、已签收、质量/无理由 | 主管审批 |
| R3 | >500、特殊品类、已发货、少件/错发、签收争议 | 双人/主管审批 |
| R4 | 投诉、威胁、监管、诈骗、账号安全 | 主管/紧急接管 |
| R5 | 改地址、改订单、跨系统写操作 | 运营审批 |

> 数值只是初始阈值，必须由商家政策配置；`tickets_v1` 的 20 条 human 可作为校准集，不是最终规则。

### 4.4 回复结构

```text
我理解你的问题是：<复述>
我查到：<订单/物流/政策/金额>
处理结论：<可退/不可退/需审核/需补件>
下一步：<动作/时间/需要你做什么>
依据：<政策版本/引用>
```

禁止：

- 只回“无法处理/转人工”；
- 不解释金额/运费/期限；
- 对高风险动作做口头承诺；
- 对投诉只道歉不处理；
- 把内部审核说成“已转人工客服”。

### 4.5 毒点 Playbook（方案层）

| Playbook | 触发 | 必查事实 | 决策 | 输出 |
| --- | --- | --- | --- | --- |
| 高金额退款 | 金额 > 阈值或高风险品类 | 订单状态、签收天数、商品、已退金额、政策 | 可退但需主管审批 | proposal + breakdown + 审批卡 |
| 特殊品类 | 定制/定做/不可退 | 商品属性、是否影响二次销售、政策例外 | 默认拒绝/人工复核 | 拒绝依据 + 替代方案 |
| 签收争议 | 物流已签收但买家称未收到 | 物流轨迹、签收人、时间、地址、订单金额 | 不直接退款；理赔/复核 | 证据卡 + 工单 + 买家回复 |
| 部分退 | 只退其中一件/一半 | 商品明细、数量、金额分摊 | 当前不支持自动部分退 | 明确边界 + 人工/工单 |
| 退款时效 | “多久到账” | 退款状态、支付渠道、政策 | 能查则答；不确定则审核 | 不承诺具体到账 |
| 投诉 | 情绪/差评/投诉 | 订单、历史、已给方案 | 共情 + 事实 + 补救；主管审核 | 处理方案 + 工单 |
| 改地址 | 已支付/已发货 | 订单状态、是否出库、地址变更规则 | 未出库可申请；已出库转运营 | 条件说明 + 审核 |
| 取消订单 | 未支付/已支付/已发货 | 支付/发货状态、库存 | 未支付自助；已支付/发货拦截 | action + 审批 |
| 换货 | 尺码/颜色/质量换货 | SKU、库存、物流、政策 | 可换则 exchange；否则退款/审核 | exchange proposal |
| 越权/隐私 | 查他人/要联系方式 | 当前用户与订单归属 | 拒绝 + 合规路径 | 审计 + 拒绝理由 |

**原则**：每个 Playbook 必须有“不能做什么”和“必须留什么痕”，否则 Agent 会在例外上越权或编造。

## 6. Agent 编排

```text
intake
  → normalize（脱敏/渠道/身份）
  → understand（意图/槽位/情绪/紧急）
  → resolve_context（订单/商品/物流/历史）
  → retrieve_policy（知识/规则版本）
  → decide（确定性资格/金额/风险）
  → propose（动作 + 回复草稿）
  → gate（auto/review/assign/emergency）
  → execute（幂等）
  → reply（品牌语气 + 依据）
  → audit（事件/指标）
  → learn（人工修改/拒绝/投诉回流）
```

**确定性边界**：

- 金额、资格、运费、时限、审批额度：规则/工具，不让 LLM 算。
- LLM 只做：理解、摘要、解释、草稿、建议分类。
- 工具白名单 + 参数校验；禁止模型传 `user_id/amount/approval`。
- 任何执行前重新校验订单状态/政策版本/幂等键。

### 6.1 为什么不是“又一个聊天客服”

| 维度 | 普通聊天客服 / 平台 bot | ERP | 本方案 |
| --- | --- | --- | --- |
| 主输出 | 回复文本 | 执行单据 | **action proposal + 证据 + 金额 + 风险** |
| 判责 | 靠关键词/商家配置 | 不判责 | 确定性规则 + 例外 playbook |
| 证据 | 引用弱/不可定位 | 单据字段 | 政策快照 + 订单/物流事实 + 可追溯 |
| 审批 | 转人工/无 | 有流程但非 AI 判责 | 风险门 + 商家内部审批 |
| 执行 | 大多不执行 | 强 | 调 ERP，不自造执行 |
| 审计 | 聊天记录 | 单据日志 | proposal/approval/execute 全链路 |
| 评价 | 解决率/转人工率 | 对账 | action/金额/审核/false approve |
| 部署 | SaaS/平台绑定 | 商家系统 | 单商家可私有化/本地 |

> 这不是“功能更多”的竞争，而是**责任链不同**：别人给答案/单据，我们给“可审批的判责结论”。公开证据未发现竞品完整覆盖该组合，但必须在访谈中证伪。

## 7. 评测方案（tickets_v1）

### 7.1 切分

- `dev` 50：开发/调 prompt/规则。
- `holdout` 25：只用于最终验收，禁止调参。
- 需补真实脱敏工单；合成集不能证明真实效果。

### 7.2 指标

| 指标 | 说明 | 建议阈值 |
| --- | --- | --- |
| Action accuracy | 数据集 9 类动作（系统 12 类） | ≥85%（holdout） |
| Refund apply/reject accuracy | 退款动作二分类 | ≥90% |
| Amount accuracy | apply 金额完全一致 | **100%**（零容忍） |
| Review recall | 应审核的被正确标记 | ≥95% |
| False auto-approve | 该审核却自动执行 | **0** |
| Answer rubric | 有依据/有下一步/不机械 | ≥4/5 |
| Mechanical reply | 首句模板/无下一步 | 0 |
| Handling time | 商家实测每单分钟数 | 下降 ≥30% |
| Audit completeness | 有 proposal/approval/execution | 100% |

### 7.3 混淆矩阵与代价

- 误自动通过（false approve）比误审核（false review）代价高：钱/合规。
- 退款 reject 误判会伤买家；用人工复核 + 申诉。
- 报告按 action 分层，不能只报总 accuracy。
- 需要记录失败样本：T-033 签收争议、T-056 时效不确定、T-057 部分退、T-061/62 投诉、T-069 改地址。

### 7.4 反作弊

- holdout 不参与 prompt/规则迭代。
- 人工审核样本不能只挑容易的。
- 不能用“转人工率下降”单独证明价值；看错误/返工/CSAT。

### 7.5 验收范围与标准

分两道门，不能混：

| 门 | 名称 | 数据 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- | --- |
| G1 | P1a 作品验收 | 75 条合成（50 dev/25 holdout）+ 真实模型 | 判责/动作/金额/审核链路可复现 | 真实商家效果、付费意愿 |
| G2 | P1b 商家试用 | 1–2 家、30–50 条真实脱敏工单、4 周 | 是否能省时/可采纳/零金额错误 | 大规模/多商家/全自动 |
| — | 生产 | 不在 P1 | — | — |

**G1 通过标准**：

| ID | 指标 | 阈值 | 证据 |
| --- | --- | --- | --- |
| A-M1 | 工单集完整 | 75 条；50 dev/25 holdout；字段齐全 | `tickets_v1` + runner |
| A-M2 | Action accuracy | holdout ≥85% | 混淆矩阵 |
| A-M3 | 退款 apply/reject accuracy | ≥90% | 分层报告 |
| A-M4 | 金额正确性 | **100%**；错一单失败 | 逐单对比 |
| A-M5 | 审核召回 | 20 条人工样本 recall = 100%；false auto-approve = 0 | 审核路由表 |
| A-M6 | 证据完整 | 有政策/订单/物流证据 ≥95%；引用不存在条款 = 0 | 证据卡 |
| A-M7 | 回复质量 | rubric ≥4/5；机械回复/无下一步 = 0 | 人工评分 |
| A-M8 | 审计完整 | proposal/approval/execute 事件 100% | 事件表 |
| A-M9 | 幂等 | 重复请求 0 重复执行 | 幂等测试 |
| A-M10 | 性能 | 查询/判责 P95 ≤3s（不含 ERP） | 运行记录 |

**G2 通过标准**（G1 不过不得进入）：

| ID | 指标 | 阈值 |
| --- | --- | --- |
| A-M11 | 商家采纳 | “可直接采纳/小改” ≥70% |
| A-M12 | 处理时间 | 查+判+办+回 人工分钟下降 ≥30% |
| A-M13 | 金额/资格错误 | **0** |
| A-M14 | 高风险漏审 | **0** |
| A-M15 | 审计/对账 | 100% 可追溯；差异可解释 |
| A-M16 | 买家体验 | CSAT 不下降；投诉/返工不上升 |

**失败即停**：

- 任何一单金额/资格错误；
- 任何一单该审却自动执行；
- 无证据/编造政策；
- 无法追溯审批人/执行结果；
- 真实商家试用中处理时间没有下降，或采纳率 <50%。

### 7.6 验收数据与测试矩阵

| 层 | 数据 | 用途 |
| --- | --- | --- |
| 合成 dev | 50 条 | 调规则/prompt；允许反复 |
| 合成 holdout | 25 条 | 只看一次；不能调参 |
| 真实 holdout | 30–50 条（G2） | 外部有效性；不训练 |
| 对抗样本 | 签收争议、部分退、高金额、特殊品类、投诉、改地址、PII | 安全/例外 |

必须报告：

- 按 action 分层，不只报总 accuracy；
- 金额/审核的混淆矩阵；
- 失败样本与原因；
- 合成/真实分开；
- 置信区间：n=25 只能做方向判断，不能当线上效果。

| R23 | 商家不愿把数据给私有化部署 | 中 | 提供本地/私有化、最小权限、脱敏；先只读接入 |
| R24 | 售后 Agent 与 ERP 状态不一致 | 高 | 执行前读最新状态 + 幂等 + 对账 + 差异告警 |

**审查结论**：方向成立，但必须先把“商家审核”与“消费者转人工”拆开；否则会用上一版“不转人工”的 KPI 把售后责任压给 AI，产生金额/合规风险。差异化必须落在**判责 + 证据 + 审批 + ERP 编排 + 对账**，不能退化成“又一个会聊天的客服”。

## 10. 四个合理改动（推荐 A）

### 改动 A：毒点楔子——“判责 + 证据 + 审批” Copilot（推荐，3–4 周）

- 只做自营商城 + 一个垂直（鞋服/眼镜）；
- 只做退款/退货/换货三个动作；
- 工单详情：订单事实 + 政策快照 + 金额 breakdown + 证据卡 + 建议 + 审批；
- 执行先走 mock/CSV adapter，不接真实 ERP 也能演示；
- 75 条 tickets 跑 action/金额/审核，holdout 隔离。

**收益**：直接打在“只会答、不会判、不可审计”的毒点上；不接 ERP 也能验证判责价值。

### 改动 B：低风险自动执行（6–8 周）

- 接真实 ERP 售后接口（聚水潭或商家自建）；
- 低金额、未发货、规则明确退款自动；
- 幂等/对账/回滚/双人复核；
- 真实商家受控试用。

**收益**：从 Copilot 走向“替代重复执行”；需要接口与合规投入。

### 改动 C：售后数据飞轮（P1，2–3 周）

- 人工修改/拒绝/投诉回流；
- 知识/规则/评测集更新；
- 质检与 VOC 报表；
- 按 action 的 error analysis。

**收益**：长期提升；依赖 A 的真实使用数据。

### 改动 D：售后 QA/评测（如果 ERP 接不进或商家只要“判得准”）

- 不上执行，只输出判责/金额/证据/风险；
- 做离线评测、抽检、政策回归；
- 比“全自动”更容易落地，也能验证毒点。

**建议顺序**：A →（执行可行则 B 的低风险子集；不可行则 D）→ C。

## 13. 决策建议

**建议选择 A：商家售后 Copilot + 审批门**，与 08 的 D1 一致：先做“自营商城售后判责与编排 copilot”，执行调用 ERP；用 75 条合成工单做 G1 回归、再用真实工单/3–5 位从业者访谈做 G2 外部验证；在未拿到真实商家数据前，不宣称“替代人工/自动退款”。

**验收顺序**：先过 G1（A-M1–A-M10），再谈 G2（A-M11–A-M16）；G1 任何金额/审核硬门失败，不进入 G2。

如果目标是求职作品，A 也足够讲清楚“能查、能判、能建议、能审批、能审计”的差异化；如果目标是商家试用，A 是拿到真实数据的最低风险路径。
