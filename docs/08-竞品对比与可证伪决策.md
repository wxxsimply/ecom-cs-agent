## 0. 一句话决策

> **未来 4 周内不写 P1 业务代码：先用 2 周做 concierge 验证，剩余时间用于决策与必要补证。找 8 家自营商城（鞋服/眼镜优先），每家要 10 张真实工单；若 ≥4 家给材料、40 张工单“可采纳”≥70%、金额/资格错误为 0、≥3 家愿意试用 4 周，则 P1 只做“自营商城的售后判责与编排 copilot（执行调用 ERP）”；否则转向售后 QA 或停止。**

这个决策同时否掉三件事：通用客服问答、售前导购、多平台接入。

### 2.1 平台原生：深，但封闭

[E01] 报道显示，AI 店小蜜 2026-05-11 版本分标准版/高阶版；高阶版在售后侧“从回答规则延伸到办理业务，开始处理退差价、退款协商、挽单和多轮排障”，并允许商家“自主定义 AI 与人工介入的边界”。[E02] 京小智强调多智能体、售前导购/催单催付/售后跟进、7×24 与多模态，宣称服务超百万商家。

**判断**：平台内的“答 + 部分办”已经很强，且与平台交易数据深度绑定。**通用客服问答没有空位**；本次检索也未发现店小蜜/京小智覆盖自营商城与自有 OMS 的公开证据（该结论待访谈核实）。

### 2.2 客服 SaaS：全，但交付重

[E03] 七鱼把“物流智能体”“退款/退差价智能体”直接列为数字员工；[E04] 智齿的机器人配置已经细到“自定义转人工场景、知识标签加权、批量测试、按客群回复、SLA、质检”。

**判断**：“退款/物流智能体”不是空位；空位只能在**交付形态**（自有系统、私有化、可审计）或**垂直深度**上找。

### 2.3 本项目现状

P0-Lite 是“能演示、能讲清楚”的版本：22 个 pytest、50 条自建评测、`mock` 模型、样例数据、无真实 OMS/支付、`X-User-Id` 不是安全边界（[README]）。

**判断**：现在能证明的是链路正确，不能证明竞争力。

## 4. 招聘 JD 证据

### 4.1 电商客服主管（保定，5–7K，2026-05-28）[E05]

原文摘录：

> 负责售后客服团队的日常管理，包括排班、任务分配、绩效跟进与业务指导；
> 制定并优化售后处理流程与标准话术，提升团队响应时效与问题解决率；
> 处理升级客诉与疑难纠纷，协调运营、仓储、物流等部门推动闭环解决；
> 监控售后数据（退款率、纠纷率、满意度等），定期输出团队分析报告并提出改进方案；
> 对接供应商与工厂，推动批量售后问题（如批次质量异常、发错货等）的追溯与整改；
> 熟悉主流电商平台（如淘宝、京东、拼多多、抖音等）售后规则及申诉流程。

**解读**：买家的 KPI 是**流程、数据、跨部门闭环**，不是“聊天回复”。愿意为“减少退款率/纠纷率、缩短处理时长、可追溯”付费。

### 4.2 电商售后客服（宝岛眼镜，2026-10-23）[E06]

原文摘录：

> 熟练千牛、聚水潭、钉钉，有电商或眼镜行业经验优先；
> 学习产品知识、专业问题解答、配镜售后处理、维护客户关系、投诉安抚与化解等。

**解读**：一线工具栈是**千牛 + 聚水潭（ERP）+ 钉钉**，售后工作天然跨系统；“配镜售后”说明垂直类目有专门规则与证据（验光单、镜片参数）。

### 4.3 AI 训练师岗位（标题可见，正文失效）[E07]

搜索可见“店小蜜智能客服训练师”“电商 AI 训练师”“初级智能训练师”等岗位标题，说明知识/机器人配置已成为独立岗位；但正文页已失效，**不作为结论依据（U）**。

### 4.4 对项目的含义

- 若做“客服聊天”，买家是平台/运营，竞品是店小蜜/七鱼，本项目没有胜算。
- 若做“售后执行”，买家是**客服主管/财务**，价值用退款率、纠纷率、人工分钟、对账差异衡量——这与本项目已有的“确定性退款 + 证据闸门”更匹配。

## 5. 空位判断

### 5.1 拥挤区（不要进）

- 通用客服问答、售前导购；
- 平台站内售后；
- 全渠道工单/质检/呼叫中心；
- “退款/物流智能体”本身（七鱼已列，店小蜜已做）。

### 5.2 待验证的空位

> **自营商城（非平台店）+ 自有 ERP + “该不该退/退多少/依据哪条/证据够不够/异常怎么办”的判责与编排层 + 证据/审批/对账 + 可私有化。执行动作调用 ERP，而不是自己造执行引擎。**

**为什么修正了“执行”这个说法**：聚水潭开放平台文档显示，ERP 内已有退货、仅退款、换货、补发的完整售后状态流转，并支持“商家自有商城”站点与售后收货消息推送（[E09](https://open.jushuitan.com/document/2176.html)、[E10](https://open.jushuitan.com/document/2279.html)，等级 A）。**“帮商家退款”本身不是空位，ERP 已经做了。**

**为什么仍可能是空位**：

1. 平台原生主要覆盖平台站内，本次未发现其覆盖自营商城与自有 ERP 的公开证据；
2. SaaS 有退款智能体，但交付依赖集成与配置，单商家私有化成本高；
3. JD 显示一线工具栈跨千牛/聚水潭/钉钉，跨系统**判断与编排**是真实工作；
4. ERP 能“执行”，但不擅长“判责 + 金额 + 政策 + 证据 + 异常解释”；这正是本项目的确定性与证据闸门能补的位置。

**垂直选择（鞋服/眼镜）也是假设**：JD 里出现“配镜售后”，鞋服退换规则清晰、退货率高；但这是待验证的选择，不是结论。若访谈发现鞋服商家付费意愿弱，应换垂直或不限垂直。

**为什么可能不是空位**（必须证伪）：

1. 七鱼/店小蜜已覆盖“退款/退差价”，商家可能觉得够用；
2. 聚水潭 ERP 已能执行售后全流程，商家可能认为“人 + ERP 就够了”；
2. 聚水潭等 ERP 可能自带售后/退款流程；
3. 自营商城流量小、付费能力弱；
4. 商家可能只想要“少回答”，不想要“自动执行”。

**结论**：这是一个**假设**，必须用真实工单验证，不能直接开发。

## 6. 可证伪决策

### 6.1 决策陈述（D1）

> **P1 只做“自营商城的售后判责与编排 copilot”，首个垂直选鞋服/眼镜；不做售前、不做通用问答、不做多平台。先用 2 周 concierge 验证，验证通过才写 P1 代码。**

“判责与编排”指：输入一张工单，输出“订单事实 + 适用条款 + 建议动作（退款/退货/换货）+ 金额明细 + 风险 + 证据卡”；商家确认后**调用 ERP 的售后接口执行**，并留下可对账记录。执行不是本项目造的，判断与证据才是。

### 6.2 可证伪的预测（预先写死）

| 编号 | 预测 | 阈值 |
| --- | --- | --- |
| P1 | 8 家中愿意提供 10 张脱敏工单 + 政策文档 + 1 小时复核 | **≥4 家** |
| P2 | 40 张真实工单中，商家评分“可直接采纳/小改”的比例 | **≥70%** |
| P3 | 金额/资格错误（错退、多退、少退、错判资格） | **= 0**（任一单不可接受即失败） |
| P4 | 愿意试用 4 周（每周 ≥20 单） | **≥3 家** |
| P5 | 单均人工分钟数（查+判+办）下降 | **≥30%**（自报 + 抽样计时，参考项，不单独作门槛） |

> 统计边界：n=40 时，“70% 可采纳”的 95% 置信区间约 54%–83%，只能作方向判断，不能当效果证明；这也是它只用于 Go/No-Go、不用于对外宣传的原因。

### 6.3 决策规则（机械执行，不靠感觉）

| 结果 | 决策 |
| --- | --- |
| P1–P4 全部满足 | 开工 P1 纵切（范围见 6.4） |
| P1/P2 满足，P3/P4 不满足 | 缩到子场景（如只做“退款金额核算/退货资格”），再测 2 周 |
| P1 满足，P2 <50% | 不做执行，转“售后 QA/评测”或停止 |
| P1 <2 家 | 停止该方向（人群/渠道不对） |
| 任何 P3 金额错误 | 立即停，先修规则，不进入 P1 |

### 6.4 如果通过，P1 范围（只列，先不开工）

- 接 1 个 ERP 的售后能力：聚水潭「售后上传/售后收货」API，或 CSV/自建 API 三选一；本项目只做判责、金额、证据与编排；
- 3 个动作：退款、退货、换货；
- 金额规则 + 审批阈值 + 证据卡 + 对账导出；
- 1 个垂直的政策库（鞋服尺码/质量/运费，或眼镜配镜售后）。

### 6.5 明确不做（防止旧病复发）

- 不先写 P1 代码；不扩售前/优惠券/改地址/图片判损；
- 不做生产化（JWT/多实例/多租户）；
- 不追 100–150 条评测集的数字游戏；
- 不把 `mock` 结果当真实效果；
- 不为“看起来高级”上多 Agent。

## 7. 验证协议（2 周）

### 7.1 对象与招募

- 8 家：鞋服 5 家、眼镜/配镜 3 家；日单 50–500；客服 2–10 人；**自营商城**（非纯平台店）。
- 来源：本地商家群、朋友介绍、小红书/抖音商家、代运营。
- 排除：纯平台店、日单 <30、无售后团队。

### 7.2 要什么材料

1. 10 张脱敏工单（退款/退货/换货/物流异常各 2–3 张）；
2. 售后政策文档（退换、运费、时效、例外）；
3. 退款规则/审批阈值（谁批、多少金额）；
4. 1 小时复核（线上）。

承诺：只用于本次评估、脱敏、不训练、不留存原文件（签署简单书面承诺）。

### 7.3 处理建议卡（每张工单产出）

```text
工单：<编号>  渠道：<Web/微信>  订单：<脱敏号>
订单事实：状态 / 金额 / 时间 / 物流节点
适用条款：<条款号 + 版本 + 原文摘录>
建议动作：退款 / 退货 / 换货 / 转人工
金额明细：商品 / 运费 / 已退 / 本次
风险：金额超限 / 证据不足 / 政策冲突
证据：订单快照、物流记录、条款链接
需人工确认：是/否
```

### 7.4 评分 rubric

| 分 | 含义 |
| --- | --- |
| 5 | 可直接采纳 |
| 4 | 小改后采纳（改措辞/补充信息） |
| 3 | 大改后采纳（改动作/金额） |
| 2 | 不可用（但方向对） |
| 1 | 错误（含金额/资格错误，单独计数） |

记录：每单耗时、是否需要查额外系统、商家原话。

### 7.5 偏差控制

- 不告诉商家“这是 AI 生成的”，只说“处理建议”；
- 同一商家的工单随机打乱，避免顺序暗示；
- 至少 2 人复核（主管 + 客服）；
- 区分“礼貌分”（说好但不用）与“行为分”（愿意给下一批工单/试用）；
- 明确告知这是小样本（n=40），结论只作方向判断，不作效果承诺。

### 7.6 时间表

| 天 | 动作 | 产出 |
| --- | --- | --- |
| D1–D2 | 招募 8 家、发材料清单 | 4 家确认 |
| D3–D5 | 收 40 张工单 + 政策；做建议卡 | 首批 20 张 |
| D6–D8 | 复核、评分、记录原话 | 40 张评分 |

## 9. 反方与置信度

| 反方观点 | 我的回应 | 什么会让我改变决策 |
| --- | --- | --- |
| “七鱼已经有退款智能体” | 有，说明“退款执行”已商品化；本项目只做执行之前的判责/金额/证据 | 若 8 家中 ≥5 家已在用七鱼退款智能体且满意 → 放弃 |
| “聚水潭自带售后” | **已确认**：售后上传覆盖退货/仅退款/换货/补发，支持自有商城（E09/E10）。但 ERP 不负责判责、金额解释、证据与异常话术 | 若 4 家中 ≥3 家说“人+ERP 足够，不需要判责层” → 放弃或转 QA |
| “自营商城付费能力弱” | 所以先做 concierge，不先做产品 | 若 4 家愿试用但 0 家愿付费 → 转 B |
| “8 家样本太小” | 是方向判断，不是效果证明 | 若结果两极分化 → 扩到 15 家再判 |
| “concierge 不能证明规模化” | 先证需求，再证工程；规模化是 P2 | 若需求成立但单均成本 > 人工 → 停 |
