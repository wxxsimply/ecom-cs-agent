## 1. 背景与范围

本轮来自 3 条用户反馈：

1. **已签收订单必须有历史物流轨迹**，客服查询时能看到完整签收过程，工作过程要留痕。
2. **用户询问物流进度时**，除当前状态外，还要展示预期流程；尚未发生的步骤用灰色提示，不能伪装成已完成。
3. **用户提出范围外问题**时，要礼貌抱歉、明确说无法处理，然后提示当前可服务的功能，不能强行编造答案。

**本轮只做设计**：不修改接口、数据库、前端或种子数据。实施时按本文和 02 方案对齐。

**非目标**：

- 不接真实承运商 API；历史轨迹来自 `shipments/events_json` 和种子数据。
- 不承诺精确到达时间；只展示“预计流程”，不展示未来日期。
- 不把范围外问题做成 RAG 拒答；两者语义和文案要区分。
- 不重做整个对话页。

## 2. 需求澄清

### 2.1 三条明确需求

| ID | 需求 | 当前问题 | 优先级 |
| --- | --- | --- | --- |
| L1 | 已签收订单必须保留完整历史轨迹，查询时返回全部节点，最后一条为“已签收” | `logistics_summary()` 只返回 `events[-3:]`；部分已签收订单（1001/1004/1005/1006/1007/1009）没有 shipment 记录 | P0 |
| L2 | 物流进度 = 当前状态 + 预期流程；已完成/当前/待完成分开展示，待完成步骤标灰 | 现在只返回状态和轨迹，没有“预期流程”概念，用户不知道后面还有什么 | P0 |
| L3 | 范围外问题：礼貌抱歉 + 明确“无法处理” + 列出可服务功能；不编造、不调用业务工具 | `classify()` 的兜底返回 `chitchat`，`generate()` 只回“你好，我是小猫…”，既没有道歉也没有能力清单 | P0 |
| L4 | 修复不能回归现有订单/物流/退款/引用/SSE | 改 schema/模板容易破坏现有 `logistics_summary`、`done`、前端渲染 | P0 |

### 2.2 范围边界

**属于“范围外”**：

- 天气、新闻、股票、医疗、法律、代码、翻译、闲聊八卦等与商城客服无关的问题；
- 要求客服执行未实现的操作：改地址、改手机号、取消已支付订单、直接打款、查他人订单；
- 知识库没有、且不属于平台规则/商品/订单/售后的问题。

**不属于“范围外”**：

- “你能做什么/你是谁” → 能力介绍，不道歉；
- “你好/谢谢” → 普通打招呼；
- “退款规则是什么” → 知识库 RAG，即使答案缺失也走 D3 拒答 + 转人工，不是范围外；
- “我要退款但没给订单号” → 订单选择中断，不是范围外。

### 2.3 验收标准

| # | 验收 |
| --- | --- |
| A1 | 所有 `status=delivered` 的种子订单都有 shipment；`events` 至少 5 条，最后一条为“已签收”，`history_complete=true` |
| A2 | 查询 `订单 1001 到哪了` 返回完整历史，而不是只返回最后 3 条；轨迹按时间升序 |
| A3 | 物流回复包含 7 步预期流程；已完成/当前/待完成状态正确；待完成步骤有灰色样式与“待完成”文字，且不显示未来具体时间 |
| A4 | 回复中出现灰色提示：“以下为预计流程，实际以承运商轨迹为准” |
| A5 | 问“今天天气怎么样”返回：抱歉 + 无法处理 + 4 项可服务功能；无引用、无工具调用、无编造 |
| A6 | 问“邮费是多少”仍走 RAG；问“你好”仍走问候；问“转人工”仍转人工 |
| A7 | 现有 13 个 pytest、RAG 气泡、引用抽屉、退款确认、订单中断全部不回归 |

## 4. 方案设计

### 4.1 数据与留痕（L1）

#### 4.1.1 数据模型

P0-Lite 保留现有 `Shipment.events_json`，但把它当作**只追加**的轨迹：

```text
Shipment
  order_id, carrier, tracking_no, status
  events_json: [
    {"time": "2026-10-23 09:12", "text": "商家已发货"},
    {"time": "2026-10-23 14:30", "text": "顺丰已揽收"},
    {"time": "2026-10-24 08:05", "text": "到达上海转运中心"},
    {"time": "2026-10-25 07:40", "text": "派送中"},
    {"time": "2026-10-25 16:20", "text": "已签收，签收人：本人"}
  ]
```

规则：

- 事件只追加，不覆盖、不截断；`logistics_summary` 返回全部事件。
- 事件按 `time` 升序；同一时间按稳定顺序；重复事件按 `(time,text)` 去重。
- 已签收订单必须包含“已签收”事件；`orders.delivered_at` 与最后一条签收事件时间对齐。
- 若历史数据缺失：返回 `history_complete=false` + “历史轨迹缺失，已记录工单”，**不得伪造轨迹**。
- P0-Lite 不新建 `shipment_events` 表；完整 P0 再迁移到规范化事件表（`shipment_id/event_time/status/description/source/created_at`），便于审计和分页。

#### 4.1.2 种子数据

给所有已签收订单补 shipment（数量不少于 5 条）：

| 订单 | 承运商 | 关键轨迹 |
| --- | --- | --- |
| 1001 | 顺丰 | 已发货 → 已揽收 → 转运中心 → 派送中 → 已签收 |
| 1004 | 京东物流 | 已发货 → 已揽收 → 转运中心 → 派送中 → 已签收 |
| 1005 | 中通 | 已发货 → 已揽收 → 运输中 → 派送中 → 已签收 |
| 1006 | 圆通 | 已发货 → 已揽收 → 转运中心 → 派送中 → 已签收 |
| 1007 | 顺丰 | 已发货 → 已揽收 → 运输中 → 派送中 → 已签收 |
| 1009 | 中通 | 已发货 → 已揽收 → 到达转运中心 → 派送中 → 已签收（已退款订单也保留历史） |

种子幂等：按 `order_id` 查重，不覆盖已有轨迹；已有订单只补缺失事件，不重复插入。

### 4.2 进度 schema（L2）

`logistics_summary()` 返回：

```json
{
  "order_id": "1001",
  "status": "已签收",
  "carrier": "顺丰",
  "tracking_no": "SF1234567890",
  "history_complete": true,
  "events": [
    {"time": "2026-10-23 09:12", "text": "商家已发货"},
    {"time": "2026-10-25 16:20", "text": "已签收，签收人：本人"}
  ],
  "progress": {
    "steps": [
      {"key": "placed", "label": "已下单", "state": "done", "time": "2026-10-22 20:10"},
      {"key": "paid", "label": "已支付", "state": "done", "time": "2026-10-22 20:12"},
      {"key": "packed", "label": "已出库", "state": "done", "time": "2026-10-23 09:12"},
      {"key": "picked_up", "label": "已揽收", "state": "done", "time": "2026-10-23 14:30"},
      {"key": "in_transit", "label": "运输中", "state": "done", "time": "2026-10-24 08:05"},
      {"key": "out_for_delivery", "label": "派送中", "state": "done", "time": "2026-10-25 07:40"},
      {"key": "delivered", "label": "已签收", "state": "done", "time": "2026-10-25 16:20"}
    ],
    "hint": "以下为预计流程，实际以承运商轨迹为准"
  }
}
```

**状态映射**：

| 订单/物流状态 | 当前步骤 | 说明 |
| --- | --- | --- |
| `pending_payment` | `placed` | 未支付，后续全部 pending |
| `paid` | `paid` | 已支付，未出库 |
| `shipped` + “已发货” | `packed` | 已出库 |
| `shipped` + “已揽收” | `picked_up` | 已揽收 |
| `shipped` + “运输中” | `in_transit` | 运输中 |
| `shipped` + “派送中” | `out_for_delivery` | 派送中 |
| `delivered` | `delivered` | 全部 done |
| `cancelled` | 异常流程 | 不展示正常进度，显示“订单已取消” |
| `refunded` | 异常/完成 | 保留已签收轨迹；显示“已退款”，不把退款当作物流步骤 |

**关键约束**：

- `steps` 固定 7 步，顺序不可变；`state` 只能是 `done / current / pending`。
- 未来步骤不显示具体时间、不显示 ETA；只显示灰色“待完成”。
- `hint` 固定为“以下为预计流程，实际以承运商轨迹为准”，始终用灰色提示条展示。
- 已签收订单所有步骤 `done`，但仍展示 hint，表示流程是标准模板。
- 历史事件与 progress 分开：`events` 是真实轨迹，`progress` 是标准流程；不要把“预期”混进真实轨迹。

### 4.3 物流回复与前端展示（L2）

**回复结构**：

```text
订单 1001 当前物流状态：已签收

运输进度
✓ 已下单        2026-10-22 20:10
✓ 已支付        2026-10-22 20:12
✓ 已出库        2026-10-23 09:12
✓ 已揽收        2026-10-23 14:30
✓ 运输中        2026-10-24 08:05
✓ 派送中        2026-10-25 07:40
✓ 已签收        2026-10-25 16:20

以下为预计流程，实际以承运商轨迹为准（灰色提示）

历史轨迹
- 2026-10-23 09:12 商家已发货
- 2026-10-23 14:30 顺丰已揽收
- 2026-10-24 08:05 到达上海转运中心
- 2026-10-25 07:40 派送中
- 2026-10-25 16:20 已签收，签收人：本人
```

**前端组件**：

- `timeline`：7 行/横向步骤；`done` 用实心勾，`current` 用强调色，`pending` 用灰色虚线圆点 + 文字“待完成”。
- 不使用颜色作为唯一信息：每步有 `aria-label`/文字状态；`pending` 加 `aria-disabled="true"`。
- 灰色提示条 `.progress-hint`：浅灰背景、灰色文字、不可点击；文案固定。
- 历史轨迹独立列表，完整展示，不截断；已签收事件加签收人/时间。
- 移动端 342px：timeline 纵向排列，文字不换行溢出；hint 在 timeline 下方。
- 物流文本仍走现有 `.msg-text` 气泡，不新增消息类型；`progress` 可渲染为 `<ol class="timeline">`。

**文案边界**：

- “预计流程”只能解释标准步骤，不能写“预计明天到”；
- 若订单已取消/已退款，先说明异常状态，再决定是否展示历史；
- 不把“已签收”写成“已送达”以外的承诺。

### 4.4 范围外兜底（L3）

#### 4.4.1 意图与路由

新增第 10 个意图 `out_of_scope`，保留 `chitchat`：

```text
chitchat       → 你好/谢谢/你是谁/你能做什么（能力介绍）
out_of_scope   → 其他无法归类的请求
```

规则：

- 先匹配业务关键词（退款/订单/物流/政策/商品/人工），命中即走原链路。
- 明确的能力询问（“你能做什么”）→ 能力介绍，不道歉。
- 无业务关键词、无订单号、无政策词 → `out_of_scope`。
- “今天天气/帮我写代码/股票/翻译” → `out_of_scope`。
- “我要改地址/取消已支付订单” → 不直接执行；说明当前不支持 + 转人工（属于“范围外操作”，不是普通闲聊）。

**路由**：`out_of_scope` → `out_of_scope_reply`，直接返回模板，不进 RAG、不调用订单/退款工具；`chitchat` 仍走原来的问候分支。新增意图后总数为 10，原 9 类路由不变。

#### 4.4.2 回复模板

```text
抱歉，这个问题我暂时无法处理，我不能直接帮你完成。

我可以帮你：
- 查询订单状态和物流进度
- 办理退换货/退款申请
- 解答运费、会员、发票等平台规则
- 转接人工客服

你可以直接说“查订单 1001”或“我要退款”。
```

约束：

- 第一句必须包含“抱歉”+“无法处理”语义，不能只说“我不知道”；
- 必须列出 3–4 项**已实现**能力，不能列“改地址/催发货/直接退款”等未实现功能；
- 不生成引用、不调用订单/退款工具、不写 `done.citations_used`；
- 状态为 `refused`，`reason_code=out_of_scope`；
- 如果用户随后给业务问题，正常进入原链路；
- 可选提供快捷按钮（查订单/退款/转人工），但不能自动执行写操作。

#### 4.4.3 与 D3 拒答的区别

| 场景 | 回复 | 后续 |
| --- | --- | --- |
| 范围外（天气/代码） | 抱歉 + 无法处理 + 能力清单 | 不转人工，除非用户明确要求 |
| 范围内但知识库无答案 | 暂未查到明确规则 + 转人工/工单 | 建工单、入问题池 |
| 业务问题但缺槽位 | 追问/订单选择卡 | 继续原流程 |

### 4.5 异常与边界

| 情况 | 处理 |
| --- | --- |
| delivered 但无 shipment | `history_complete=false`；显示“已签收，历史轨迹缺失，已记录工单”；不伪造 |
| 有 shipment 但无已签收事件 | 用 `orders.delivered_at` 作为“签收时间”展示，标记轨迹不完整 |
| 事件时间倒序/重复 | 排序、去重、保留原始文本 |
| 时区 | 统一按 `Asia/Shanghai` 展示；存储保留 ISO/本地时间字段 |
| 已取消/已退款 | 不展示正常 7 步进度；展示异常状态 + 已有历史 |
| 范围外问题含 PII | 先脱敏，再走范围外模板；不写日志明文 |
| 用户说“你能做什么” | 能力介绍，不道歉 |
| 用户说“转人工” | 直接 handoff，不先范围外模板 |

## 5. 对抗性审查

| # | 风险 | 级别 | 修法 |
| --- | --- | --- | --- |
| R1 | 为了“补全轨迹”而伪造未发生的物流事件 | 阻断 | 只从 shipment 事件/订单签收时间取数；缺失时标 `history_complete=false`，不编造 |
| R2 | 只改 UI，后端仍 `events[-3:]` | 高 | `logistics_summary` 返回全部事件；加单测断言 1001 至少 5 条 |
| R3 | 预期流程被用户当成真实进度 | 高 | `progress` 与 `events` 分字段；pending 灰色 + “待完成” + 固定 hint；不显示未来时间 |
| R4 | `paid` 订单把“已揽收”误标为 done | 高 | 当前步骤由订单状态 + 最新事件推导；后续全部 pending |
| R5 | 已签收订单只显示“已签收”，没有历史 | 高 | 种子补齐 1001/1004/1005/1006/1007/1009；前端历史列表不截断 |
| R6 | 范围外问题误伤业务问题 | 高 | 业务关键词/订单号/政策词优先；用“邮费/退款/订单 1003/转人工”回归测试 |
| R7 | 范围外模板承诺未实现功能 | 高 | 能力清单只列已实现 4 项；加配置/测试锁定 |
| R8 | 把“知识库缺失”也回成“范围外” | 中 | D3 与 out_of_scope 分开；知识库缺失仍转人工/入池 |
| R9 | 灰色只用颜色，色盲/读屏不可用 | 中 | 增加“待完成”文字、虚线、`aria-disabled`；对比度检查 |
| R10 | 物流事件多了导致气泡过长 | 中 | 历史列表可折叠/滚动；默认展示完整但限制高度；不截断数据 |
| R11 | 时区/排序导致签收时间错位 | 中 | 统一 Asia/Shanghai，排序去重，签收事件与 delivered_at 对齐 |
| R12 | 改动破坏现有 SSE/退款/订单卡 | 高 | 不新增 SSE 事件；`done.status=refused` 沿用；现有 13 个 pytest + Playwright 回归 |

**结论**：方案可行；实施前必须先补种子数据和服务层全量事件，否则前端 timeline 只是“看起来有”，实际仍是残缺数据。

## 7. 实施顺序（后续，不在本轮）

1. 补 `scripts/seed.py`：6 笔已签收订单的 shipment + 5 条以上事件（含已签收），幂等。
