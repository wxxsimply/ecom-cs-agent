## 2. 项目背景与问题定义

### 2.1 背景

电商客服的日常问题高度集中：运费、退换货、订单状态、物流进度、商品规格、发票与优惠。大量问题重复、答案有明确政策依据，但同时又夹杂着「那它能退吗」「这个和刚才那单一样吗」这类依赖上下文的半截话。

传统方案有三类不足：

1. **纯 FAQ/关键词机器人**：只能匹配固定问法，换个说法就答不上来；多轮上下文几乎不可用。
2. **纯 RAG 问答**：能回答政策问题，但无法查订单、查物流、发起退款；遇到知识库没有的问题容易编造。
3. **纯 Agent 自由发挥**：灵活，但退款金额、运费承担、时效承诺等业务铁律不可控，线上风险高。

### 2.2 问题陈述

> 面向单商家自营商城，构建一个中文电商智能客服 Agent：对政策/商品问题给出**有出处、可追溯**的回答；对订单/物流问题调用**受控工具**查询；对退款/售后走**确定性子流程**；证据不足时**敢拒答、能转人工**；并把答不上来的问题沉淀为**可审核、可回写**的数据飞轮。

### 2.3 为什么是「Workflow + Agent」而不是二选一

- **确定的事交给流程**：退款资格、金额上限、运费承担、订单归属校验，必须按规则执行，不能让模型自由裁量。
- **需要判断的事交给 Agent**：用户表达模糊、需要多步工具调用、需要结合上下文推理时，由 Agent 在受控工具集内做 ReAct 循环。
- **两者共用一套状态与可观测**：LangGraph 负责把分流、子流程、中断恢复、Agent 循环串成一张图。

## 3. 产品定位与目标

### 3.1 一句话定位

一个面向单商家自营商城的 Web 端 AI 客服 Agent，覆盖售前商品咨询、售中订单/物流查询、售后退款/换货与人工兜底，强调**证据可追溯、业务可约束、问题可闭环**。

### 3.2 目标

| 维度 | 目标 | 衡量口径 |
| --- | --- | --- |
| 用户价值 | 大多数常见问题一次对话解决 | P0 意图范围内自助解决率 ≥ 60%（未转人工且用户未重复追问） |
| 回答可信 | 政策/商品回答必须有出处，不编造 | 评测集上引用覆盖率 100%，引用准确率 ≥ 90%，忠实度 ≥ 95% |
| 业务安全 | 退款/运费等高风险动作不越权、不越界 | 高风险动作 100% 经规则引擎或人工确认；生产模式越权订单查询 0 例 |
| 体验 | 首个字快，长回答不阻塞 | 首 token P95 ≤ 1.5s（加速路径；CPU 2.0–2.5s）；完整回答 P95 ≤ 8s（RAG）/12s（工具） |
| 可运营 | 答不上的问题能沉淀、能审核、能回写 | 拒答/点踩/自检失败 100% 进入问题池；审核闭环率 ≥ 80% |
| 可排障 | 一次回答可还原完整调用链 | 每个请求有 trace_id；节点、检索、工具、token 均可查 |
| 成本 | 单轮/单会话成本可控 | 单轮 LLM 成本 ≤ ¥0.03；5 轮会话 ≤ ¥0.15；超支降级 |

### 3.3 非目标（本期不做）

- ❌ 多商家/多租户 SaaS、商家入驻、计费结算。
- ❌ 电话语音客服、外呼、主动营销、企微/抖音等多渠道接入。
- ❌ 完整 OMS/WMS/支付系统；只做订单、物流、退款的**适配层**与样例数据。
- ❌ 自研大模型、从零训练 LLM；微调仅作为 P2 的旁路实验。
- ❌ 全自动执行退款打款；MVP 只做到「创建退款申请/工单」，资金操作仍由业务系统或人工完成。
- ❌ 复杂视觉/图片理解、多语言；MVP 仅中文文本。

## 4. 用户与角色

| 角色 | 是谁 | 核心诉求 | 主要触点 |
| --- | --- | --- | --- |
| 消费者（C 端） | 商城已登录用户 | 快速得到准确答案；能查自己的订单；不行就转人工 | 聊天窗口、订单选择弹窗、引用详情、评价按钮 |
| 人工客服 | 售前/售后坐席 | 接手时能看到上下文、意图、已查证据，不重复问用户 | 转人工卡片、工单、会话摘要 |
| 知识运营 | 负责 FAQ/政策/商品知识 | 知道用户问什么答不上来；能审核、补知识、发布 | 运营工作台：问题池、知识库、审核队列 |
| 研发/运维 | 开发和维护系统 | 能定位一次回答为什么错、慢、贵 | 链路可视化、Langfuse、指标看板、日志 |

### 4.1 核心用户故事

- 作为消费者，我问「邮费是多少」，希望直接看到分档规则和出处，而不是一段没有依据的笼统回答。
- 作为消费者，我上一句问了订单 1001，下一句只问「那它能退吗」，希望系统知道「它」指的是哪一单。
- 作为消费者，系统不确定是哪一单时，希望它把最近订单列出来让我选，而不是瞎猜。
- 作为消费者，问题超出知识库时，希望系统明确说「暂未查到」，并帮我转人工，而不是编一个答案。
- 作为知识运营，我希望按被问频次处理问题池，补完答案后一键回到知识库。
- 作为人工客服，我接手时希望直接看到会话摘要、用户意图、订单号和已检索到的证据。

## 5. 核心场景与验收样例

### S1 政策问答：运费是多少（✅ 来自 S5）

**前置**：用户已登录；知识库已录入运费规则。  
**流程**：用户问「邮费是多少」→ 意图识别为政策咨询 → 混合检索命中运费规则 → 置信度通过 → 流式生成分档回答，句末带 `[1][10]` 等引用。  
**必须包含**：包邮门槛、未满门槛的基础运费、偏远地区附加费、港澳台/海外限制、会员免运费、积分抵扣、退换货运费承担。  
**验收**：回答中的每个政策数字都能在引用块中找到；引用可展开查看来源；不得出现知识库之外的自创规则。

### S2 多轮指代：那它能退吗（✅ 来自 S6）

**前置**：上一轮已查询订单 1001，已知商品与签收时间。  
**流程**：用户问「那它能退吗」→ 指代消解把问题补成「订单 1001 中的商品能否退货」→ 路由到售后子流程 → 校验订单归属、签收时间、商品品类 → 给出可退/不可退结论与依据。  
**验收**：不追问「你说的是哪一单」；结论与订单真实状态一致；涉及金额/时效时给出规则出处或数据来源。

### S3 证据不足：宁可拒答（✅ 来自 S6）

**前置**：知识库没有「宠物粮是否支持拆封退」的明确规则。  
**流程**：检索返回的证据相关度低于阈值 → 置信度闸门拦截 → 输出「暂未查到明确规则，已为你转人工」→ 创建工单并携带上下文。  
**验收**：不得生成具体退款承诺；必须出现转人工/工单入口；问题进入问题池。

### S4 缺槽位：订单选择后断点续接（✅ 来自 S6）

**前置**：用户说「帮我退款」，但未提供订单号，且名下有多笔订单。  
**流程**：售后子流程发现缺少 `order_id` → 拉取最近订单 → 以选项卡形式中断（interrupt）→ 用户选择订单 → 从断点恢复，继续校验退款资格。  
**验收**：中断期间会话状态不丢；恢复后不重复询问已知信息；用户取消时能优雅结束。

### S5 业务工具：查物流/查订单（✅ 来自 S3、S4）

**流程**：识别为订单/物流意图 → 校验订单归属 → 调用只读工具 → 将结构化结果转成自然语言 → 流式返回。  
**验收**：只能查当前用户自己的订单；工具超时/失败时有降级话术；不把工具原始 JSON 直接吐给用户。

### S6 数据飞轮：点踩后补知识（✅ 来自 S4）

**流程**：用户对回答点踩并选择「答案不准确」→ 反馈落库 → 问题进入问题池（附带检索快照）→ 运营审核 → 补写知识/修正切分 → 发布并向量化 → 回归评测通过。  
**验收**：反馈 100% 可追溯到原消息与 trace；审核动作有审计记录；回写后同一问题可被新知识命中。

### S7 运营与排障（✅ 来自 S3）

**流程**：运营打开工作台，看到今日会话量、转人工率、低置信度问题、点踩列表；点开一条 trace，看到意图、路由、检索 TopK、重排分数、工具调用、token 与耗时。  
**验收**：任一线上回答可在 3 次点击内定位到 trace；敏感信息脱敏展示。

## 6. 范围与优先级

### 6.1 P0（MVP，必须端到端跑通）

| 模块 | P0 内容 |
| --- | --- |
| 接入 | Web 聊天页；`user_id` 请求头模拟登录；会话创建/列表/历史；SSE 流式输出 |
| 理解 | 指代消解 + 9 类意图识别 + 关键槽位抽取（订单号、商品、时间） |
| 路由 | 9 类意图收敛到 5 个出口；低置信度先澄清 |
| RAG | 知识入库、结构感知切分、BGE-M3 向量 + BM25 双路召回、RRF、Reranker、TopK 引用 |
| 闸门 | 检索/重排置信度闸门；低置信度拒答 + 转人工 |
| 工具 | 订单查询、订单列表、物流查询、退款资格校验、建工单、转人工 |
| 售后 | 退款/换货确定性子流程；缺订单号中断/恢复；规则引擎判定 |
| 生成 | 带引用回答、拒答模板、兜底话术、SSE 逐字输出 |
| 记忆 | 近 N 轮原文 + 滚动摘要；会话状态持久化 |
| 飞轮 | 点踩/拒答/自检失败入问题池；最小审核与回写流程 |
| 可观测 | Langfuse Cloud/自部署或本地 NDJSON；请求级 token/耗时/工具记录 |
| 工程 | FastAPI + SQLAlchemy + MySQL + Milvus + Docker Compose；种子数据与评测集 |

### 6.2 P1（体验与运营增强）

- 运营工作台完整版：问题池聚类、按频次排序、审核分配、知识版本管理。
- MCP 外部工具接入与 Skill 技能包机制。
- 安全专项增强：注入分类器、内容审核、限流、依赖扫描；P0 已含 PII 脱敏、指令层级与工具白名单。
- 评测自动化：CI 回归、LLM-as-judge、A/B 实验。
- 人工客服工作台对接（真实坐席系统/IM）。
- 多轮摘要质量优化、长期记忆（用户偏好/常购品类）。

### 6.3 P2（演进）

- 多租户/多商家、多渠道（企微、抖音、App）。
- 语音客服、图片理解、多语言。
- RoBERTa 意图分类器微调 / 小模型蒸馏，替代部分 LLM 调用。
- 退款自动打款、与真实 OMS/支付系统深度集成。
- 主动服务（物流异常预警、售后跟进）。

### 8.1 九类意图

| # | 意图 ID | 中文 | 典型问法 | 关键槽位 | 默认出口 |
| --- | --- | --- | --- | --- | --- |
| 1 | `policy_qa` | 政策咨询 | 邮费多少、怎么退、发票怎么开 | 政策主题、订单号（可选） | RAG |
| 2 | `product_qa` | 商品咨询 | 这个材质是什么、有货吗、适合几岁 | 商品/SKU、属性 | RAG |

| 5 | `refund_request` | 退款退货 | 我要退款、这个能退吗、退款到哪了 | 订单号、原因、金额 | 售后工作流 |
| 6 | `after_sales` | 换货/售后 | 能换货吗、少发了一件、坏了 | 订单号、商品、问题类型 | 售后工作流 |
| 7 | `complaint` | 投诉建议 | 客服态度差、我要投诉、太失望了 | 订单号（可选）、诉求 | 转人工 |

| 9 | `human_handoff` | 转人工 | 转人工、叫真人、你解决不了 | 无 | 转人工 |

### 8.2 五个出口

| 出口 ID | 名称 | 承接意图 | 说明 |
| --- | --- | --- | --- |
| `rag` | 知识问答 | policy_qa、product_qa | 检索 → 重排 → 闸门 → 带引用生成 |
| `business_tool` | 业务工具 | order_query、logistics_query | 鉴权 → 只读工具 → 结构化转自然语言 |
| `after_sales_workflow` | 售后工作流 | refund_request、after_sales | 确定性子流程 + 工具 + 规则引擎 |
| `direct_reply` | 直接回复 | chitchat | 轻量回复，不调 RAG/工具 |
| `human_handoff` | 转人工 | complaint、human_handoff、低置信度/高风险例外 | 安抚 + 上下文包 + 工单 |

### 8.3 路由规则

1. **明确转人工优先**：用户说「转人工/真人」时，不被其他意图覆盖。
2. **投诉不辩解**：投诉先安抚，再转人工/建工单，不进入 RAG 长篇解释。
3. **高风险不交给 Agent 自由发挥**：退款、金额、时效承诺必须走售后工作流或人工。
4. **低置信度先澄清**：意图置信度低于阈值，且候选意图差异大时，先问一个二选一问题。
5. **槽位缺失可中断**：订单号缺失但可枚举时，中断让用户选，不猜。
6. **证据不足不生成**：RAG 置信度低于阈值时拒答/转人工，不允许「根据常识」补全。

## 9. 业务规则（基线）

> 以下规则来自需求方截图（S5）与通用电商实践。标注「待确认」的，上线前必须由业务方确认；所有规则应配置化，不写死在 Prompt 里。

### 9.1 运费规则（✅ 来自 S5，数值待业务复核）

| 场景 | 规则 |
| --- | --- |
| 包邮门槛 | 单笔订单实付满 **99 元** 包邮 |
| 未满门槛 | 收取 **6 元** 基础运费 |
| 偏远地区 | 新疆、西藏、内蒙古部分区域：基础运费上加收 **12 元** 附加运费；附加部分不参与包邮，配送时效顺延 **2–4 天** |
| 港澳台及海外 | 暂不支持自营配送 |
| 会员免运费 | 金卡会员每月 **3 次**、银卡会员每月 **1 次** 免运费，可直接抵扣基础运费 |
| 积分抵运费 | **100 积分抵 1 元**，单笔最多抵 **30 元**；可抵扣未包邮时的 6 元运费，抵满即视为包邮 |
| 退换货运费 | 无理由退货/非质量问题换货：运费由用户承担；质量问题、错发、漏发：运费由平台承担 |

**回答要求**：用户只问「邮费多少」时，先给包邮门槛与基础运费，再补偏远/会员/积分；不要一次性倾倒全部规则。引用必须能定位到对应条目。

### 9.2 退款/售后规则（🟡 建议基线，待业务确认）

| 规则 | 建议值 |
| --- | --- |
| 无理由退货 | 签收后 **7 天**内，商品完好、不影响二次销售 |
| 质量问题 | 签收后 **15 天**内，平台承担退换货运费 |
| 特殊品类 | 定制品、生鲜、拆封贴身用品、虚拟商品等不支持无理由退货（可配置） |
| 退款金额 | 不得超过实付金额；已使用优惠/积分按业务规则分摊 |
| 订单状态 | 已取消/已完成/已退款等状态不可重复发起 |
| 高风险 | 单笔退款 > **500 元**、特殊品类、已发货仅退款 → 人工审核 |
| 状态流转 | `draft → pending_review → approved → returning → received → refunded`；异常分支 `rejected/cancelled` |

### 9.3 订单与数据权限

- 用户只能查询/操作自己的订单；`user_id` 从会话/Token 中取，绝不信任模型生成的用户标识。
- 订单号、运单号、退款单号在日志中脱敏展示。
- 人工客服/运营访问需单独角色权限，所有查看与修改写审计日志。

### 9.4 转人工触发条件

| 触发 | 处理 |
| --- | --- |
| 用户明确要求 | 立即转人工，带上下文 |
| 投诉/强烈负面情绪 | 先安抚，再转人工/工单 |
| 连续 2 轮无法理解 | 给菜单或转人工 |
| RAG 证据不足 | 拒答 + 转人工/工单 |
| 售后规则例外/高风险 | 转人工审核 |
| 工具连续失败 | 降级话术 + 工单 |

- 订单明细：商品、SKU、数量、单价、品类、是否可退。
- 物流：承运商、运单号、轨迹节点、异常状态。
- 退款：类型、原因、金额、状态、规则快照。
- 工单：类型、优先级、状态、上下文包。

**MVP 数据量**：≥ 20 个用户、≥ 100 笔订单、≥ 200 条物流轨迹、≥ 50 条退款记录；覆盖正常/异常/边界。

**P0-Lite 测试账户**：`u_demo` 至少 12 笔订单，覆盖 `pending_payment / paid / shipped / delivered / cancelled / refunded`，并包含高金额（>500）、特殊品类（不可无理由退）、超期（>7 天）、多物流单；种子脚本幂等，可反复执行。

### 10.3 对话与反馈数据

- 会话、消息、引用、意图、路由、token、耗时。
- 点赞/点踩、点踩原因、用户补充说明。
- 问题池、聚类、审核记录、知识发布记录。
- 全链路 trace（Langfuse）与审计日志。

### 10.4 评测数据

| 类型 | 数量（MVP） | 说明 |
| --- | --- | --- |
| 单轮政策/商品问答 | 80 | 含同义改写、表格规则 |
| 订单/物流/售后 | 40 | 含权限、状态边界 |

- Trace 中 PII 脱敏；原始订单数据不进入向量库。
- 评测集使用脱敏/合成数据，不包含真实手机号、地址。

## 11. 非功能需求

### 11.1 性能与容量

| 指标 | 目标 |
| --- | --- |
| 首 token P95 | ≤ 1.5s（加速路径；CPU 基线 2.0–2.5s） |
| 完整回答 P95 | ≤ 8s（RAG）/ 12s（工具，不含人工） |
| 意图+改写 P95 | ≤ 800ms |
| 检索+重排 P95 | ≤ 500ms |
| 工具调用 P95 | ≤ 3s（只读） |
| 并发会话 | 50 条 SSE 连接 / 8–16 个并发 LLM 生成（单实例演示） |
| 可用性 | ≥ 99.5%（MVP，非 SLA 承诺） |
| 错误率 | < 1%（不含用户主动取消） |

> 首 token/完整回答按常见 300–500 字回答测算；超过 800 字的超长回答单独统计。

### 11.2 安全

- 鉴权、越权防护、PII 脱敏、Prompt 注入防护、工具白名单、写操作确认、限流、审计。
- 密钥不入库、不进日志；数据库/对象存储不暴露公网。
- 依赖漏洞扫描与镜像最小化（P1）。

### 11.3 可维护性

- 模块边界清晰：API / Graph / RAG / Tools / Memory / Observability。
- Prompt 版本化；规则配置化；数据库迁移用 Alembic。
- 关键路径单测覆盖 ≥ 70%；核心链路集成测试必过。
- 所有外部依赖有超时、重试、降级。

### 11.4 成本

- 默认模型按输入/输出 token 计费；每次请求记录 token 与估算成本。
- 上下文预算：系统 Prompt + 摘要 + 检索证据 + 近轮对话 ≤ 8k tokens（可配）。
- 低置信度直接拒答，避免无效生成；摘要异步/按需生成。

### 11.5 兼容性

- 桌面 Chrome/Edge/Safari 最近两个大版本；移动端响应式。
- Python 3.12+；Docker Compose 一键起本地依赖。
- LLM 通过 OpenAI-compatible 接口接入，可切换供应商。

## 12. 约束与依赖

- 后端 Python 3.12 + FastAPI + SQLAlchemy + LangChain/LangGraph。
- 向量库 Milvus（单库承载 dense + sparse）；关系库 MySQL 8。
- 嵌入 BGE-M3（默认，可换 Qwen3-Embedding）；重排 bge-reranker-v2-m3。
- 可观测 Langfuse（自部署或 Cloud 二选一）；前端 React + Vite + TypeScript。
- 本地 16GB 内存推荐（API + embedding/reranker）；8GB 仅降级模式（远程 embedding/跳过 rerank）；启用 Langfuse 建议 24GB；无需 GPU（CPU/ONNX）。

**S3 分层架构**：交互层（对话页 React/Vite/TS、运营工作台、链路可视化、FastAPI）→ Agent 编排层（LangGraph Supervisor：load_context、intent、route、clarify + specialists：RAG、tools、Billing、ticket、summarize、security）→ 基础能力层（RAG 服务、工具服务、记忆服务、兜底控制、模型接入、可观测与成本）→ 数据与部署（Milvus、MySQL+SQLAlchemy、Docker Compose/云服务器）。

### 16.2 术语表

| 术语 | 含义 |
| --- | --- |
| RAG | 检索增强生成：先检索证据，再让模型基于证据回答 |
| RRF | Reciprocal Rank Fusion，倒数排名融合，用于合并多路召回 |
| 置信度闸门 | 在生成前判断证据是否足够，不足则拒答/转人工 |
| 指代消解 | 把「它/那单/这个」补成明确实体 |
| 槽位 | 完成任务所需的结构化参数，如订单号、退款原因 |
| 中断/恢复 | LangGraph 暂停等待用户输入，再从检查点继续 |
| 数据飞轮 | 把答不上来的问题沉淀、审核、回写知识库的闭环 |
| 自助解决率 | 未转人工且未在短期内重复追问的会话占比 |
