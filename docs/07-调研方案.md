## 0. 这份文档怎么用

调研不是为了写行业报告，而是为了做一个**可证伪的决策**：

> P0-Lite 之后，是继续投入 P1 / 完整 P0，还是转向或停止？如果继续，选哪个差异化方向、服务哪类商家、第一版补什么、用什么证据证明值得继续？

### 0.1 当前基线（先承认现状，避免把演示当结果）

| 项 | 现状 | 来源 |
| --- | --- | --- |
| 形态 | 单商家自营商城、Web 对话页、本地单实例 | [README](../README.md) |
| 模型 | `LLM_MODE=mock`，回答由检索/规则/模板生成 | [README](../README.md) |
| 数据 | 样例订单 12 笔、6 个会话、12 条消息；知识库为样例政策/商品/FAQ | [README](../README.md) |
| 能力 | 意图识别、混合检索（BM25 + 字符 n-gram + RRF + rerank）、订单/物流查询、退款/换货确定性子流程、SSE、中断恢复、数据飞轮雏形 | [CONTEXT §2.1](../CONTEXT.md) |
| 评测 | 50 条“机械回复/答非所问”自建集；22 个 pytest | [README](../README.md) |
| 边界 | 无真实 OMS/物流/支付；`X-User-Id` 不是安全边界；无 JWT/RBAC、无多实例、无自动打款 | [CONTEXT §2.2](../CONTEXT.md) |
| 参考基线 | MewHelp 公开项目（同一题目的课程/公开实现） | [docs/README](./README.md) |

**结论先行**：现在能证明的是“本地演示链路可跑通”，不能证明“真实商家愿意用”“真实模型效果达标”“接真实系统可行”。这三件事正是调研要回答的。

**一处需要先对齐的口径**：[CONTEXT §2.1](../CONTEXT.md) 的评测要求是 100–150 条带 gold chunk 的评测集（20% holdout），而 [README](../README.md) 与 [文档索引](./README.md) 记录的是 50 条自建集。调研开始前先确认当前以哪个为准；否则 §6 的 S6“评测可信度”无从谈起。

### 0.2 与传统“行业调研”的区别

- 不做全景扫描，只查会影响**下一步决策**的信息。
- 不信厂商口径（“80% 自动闭环”“转人工率减半”），只信**可复现的原文、原话、实测**。
- 每个结论至少两个独立来源；只有一个来源的标“待验证”。
- 调研结束时必须产出一页能签字的决策备忘录，而不是一堆链接。

## 1. 决策问题（先填空，再开始）

```text
未来 6–8 周，我应该：
  为【哪类商家/角色】，
  在【哪个渠道/系统环境】，
  把【哪个售后/服务动作】做到【什么程度】，
  第一版补什么、明确不做什么，
  用【什么指标 + 阈值】证明它值得继续。
```

建议先在下面三个方向里选一个作为调研主线（可多选但要有优先级）：

| 方向 | 含义 | 适合的目标 |
| --- | --- | --- |
| A. 求职作品 | 把“能答→能解决”讲成可验证的工程能力 | 面试、简历 |
| B. 商家试用 | 找 1–2 家自营商城做受控试用 | 产品验证 |
| C. 技术纵深 | 在 RAG/Agent 编排/评测上做深 | 学习与转型 |

> 目标不同，调研侧重点不同：A 重“可讲述的证据与差异”，B 重“付费意愿与接入可行性”，C 重“技术边界与评测方法”。**先定目标，再决定访谈和 spike 的深度。**

## 2. 五个假设与杀死条件

| # | 假设 | 最便宜的验证方式 | 什么情况下判死刑 |
| --- | --- | --- | --- |
| H1 场景 | 单商家自营商城的客服团队，痛点在“能答→能解决”，且存在可用渠道（网页/企微/微信/平台 IM） | 8 场访谈 + 要最近一单的真实流程、系统截图、渠道清单 | ≥6 家说不出具体损失、不愿试用；或自营商家普遍不用 Web 客服，产品形态不成立 |
| H2 价值 | Agent 比现有 FAQ / SaaS / 人工更快更准，且风险可控 | 20 条真实工单对照人工处理，记录省时、一次解决、错误 | 省时 <20%，或出现金额/资格类错误（零容忍） |
| H3 数据 | 政策、商品、历史工单可获得、可维护、可评测 | 要 20 条政策 + 20 个 SKU + 30 张脱敏工单；问谁维护、多久变 | 只能拿到公开样例、无法获得商家真实材料 → 只能做演示，不能宣称效果 |
| H4 技术 | 真实模型 + 真实数据下达到可用；mock 结果不可外推 | 接一个 OpenAI-compatible 模型，跑现有 50 条 + 20 条真实工单 | 引用准确 <90%、退款流程出现金额/资格错误、成本或时延不可接受 |
| H5 个人/求职 | P0→P1 工时可控，且能讲出与参考项目的差异 | 列 P1 纵切清单 + 估时 + 5 分钟脚本 + 10 个追问 | 关键依赖不在你控制内；或只能讲“我复现了 MewHelp” |

**H4 是本项目最容易自欺的一条**：现在 22 个测试全绿、50 条评测通过，但都是 `mock` 模式、自造样本。调研必须把“演示通过”和“真实可用”分开写。

## 3. 调研线（每条线当天要有产出）

### 3.0 参考项目拆解（0.5 天，先做）

读 MewHelp 项目页与课程材料，列三张清单：

1. 它做了什么（能力、架构、亮点）；
2. 它没做什么 / 做得浅的（真实系统接入、退款执行、多商家、评测方法、数据治理）；
3. 哪些是“课程标准答案”，哪些是你的独立判断。

产出：**3 条可能的差异假设**（例如：确定性退款执行、证据闸门、单商家私有化、某类目纵深）。没有差异假设，后面的访谈和竞品会失去方向。

### 3.1 桌面调研（1.5 天）

| 查什么 | 具体来源 | 要提取的内容 |
| --- | --- | --- |
| 平台官方客服 | 店小蜜、飞鸽、京小智的公开文档/演示 | 覆盖渠道、能办哪些售后动作、知识维护方式、价格/门槛 |
| 客服 SaaS | 智齿、七鱼、Udesk 等 | 工单/质检/CRM 能力，AI 是问答还是办理，部署形态 |
| 开源/课程项目 | MewHelp、Dify/Coze 上的客服模板、GitHub 同类 | 功能边界、是否可执行退款、评测方式 |
| 自营商城系统栈 | 聚水潭/旺店通/ERP/自建 OMS 的公开文档 | 订单/物流/退款接口、权限、是否支持第三方 |
| 渠道 | 网页客服、企微/微信客服、平台 IM | 自营商家实际用哪个；接入方式与限制 |
| 从业者信号 | 招聘 JD（客服主管/售后专员/客服产品） | 高频动作、系统名、考核指标 |
| 行业报告 | 艾瑞/易观/平台大促战报 | 只作背景，数字标“宣称” |

### 3.2 用户访谈（2–3 天，6–8 人）

对象配比建议：**3 个客服主管、2 个客服、2 个商家老板、1 个代运营/服务商**；以单商家自营商城为主，平台商家做对照。

**只问行为，不问态度。** 不要问“你觉得 AI 有用吗”“你会付费吗”——答案一定是礼貌的“会”。

访谈脚本见 §4。

### 3.3 竞品矩阵（1 天，与 3.1 并行）

按 §5 的表头填，至少 6 家 + 2 个平台官方客服。每格标“已核实 / 厂商宣称 / 未验证”。

### 3.4 技术 spike（1–2 天，时间盒）

目标不是做产品，是回答“这条路通不通”。清单见 §6。

### 3.5 演示与叙事验证（0.5 天）

- 写 5 分钟演示脚本：问题 → 查证 → 判责 → 执行 → 兜底，哪一步最能体现“能解决”。
- 列 10 个最可能被追问的问题（面试官或商家），逐条标“有证据 / 没证据”。
- 找 2 个不了解项目的人试听，记录他们第一句质疑。

## 4. 访谈指南

### 4.1 暖场与背景（5 分钟）

- 你们做哪些渠道（自营商城/平台店/微信/企微）？什么类目？客服几个人？每天多少咨询、多少售后？
- 你的角色是什么？哪些事必须你签字？

### 4.2 还原最近一单（15 分钟，核心）

挑**最近一单**退款/换货/物流异常，让受访者从头讲到尾：

1. 用户怎么进来的？说了什么？
2. 你开了哪几个系统？查了什么？
3. 依据哪条政策？谁写的、多久更新一次？
4. 谁批准？金额怎么定？退到哪里？
5. 花了多久？卡在哪一步？
6. 如果重来一次，你希望哪一步被自动化？

### 4.3 量化（5 分钟）

- 月咨询量 / 售后单量 / 退款金额；
- 每单人工分钟数（最好分“查”“判”“办”“回”四段）；
- 误退、纠纷、平台处罚、差评各几次；
- 新人培训多久能独立处理售后。

### 4.4 现有工具与替代方案（5 分钟）

- 现在用平台客服 / SaaS / Excel / 群聊？哪些好用、哪些不好用？
- 为什么没换？换的成本是什么？
- 如果不用任何工具，你打算怎么解决？

### 4.5 试用意愿（5 分钟）

- 如果有一个工具能【具体动作】，你愿意拿什么来试？（脱敏工单/测试账号/1 小时/政策文档）
- 愿意为什么付费？替代的是哪笔成本（人力/外包/罚款）？

### 4.6 禁忌与记录

- ❌ 不问“你觉得 AI 有用吗”“你会用吗”“这个功能好不好”。
- ❌ 不在访谈前展示方案（会得到礼貌性肯定）。
- ✅ 记录原话、数字、能否提供材料；受访者用编号（A/B/C）。
- ✅ 30 分钟内整理完，趁记忆新鲜。

## 5. 竞品矩阵模板

| 维度 | 说明 |
| --- | --- |
| 类型 | 平台官方 / 客服 SaaS / 开源或课程项目 / 外包 |
| 目标客群 | 自营商城 / 平台商家 / 多商家 SaaS |
| 渠道 | 网页 / 企微 / 微信 / 平台 IM / 电话 |
| 能力（答/查/办） | 只回答 / 能查订单物流 / 能执行退款补发 |
| 知识维护 | 官方规则 / 商家自建 / 无；谁更新 |

| 价格 | 按坐席 / 按单 / 按年；公开价 or 询价 |
| 接入门槛 | 企业主体 / ISV / 保证金 / 入云 |

## 6. 技术 spike 清单（针对当前仓库）

| ID | 要验证什么 | 怎么做 | 通过标准 |
| --- | --- | --- | --- |
| S1 | 真实模型是否可用 | 把 `LLM_MODE` 从 `mock` 切到一个 OpenAI-compatible 模型，跑现有 50 条评测 + 20 条真实工单 | 引用准确 ≥90%；拒答/兜底不退化；记录时延、token、单均成本 |
| S2 | 真实知识是否够用 | 用商家提供的 20 条政策 + 20 个 SKU 替换 `data/knowledge/` 样例 | 政策 Top8 / 商品 Top5 能命中；引用可定位到条款 |
| S3 | 退款确定性 | 用 `app/refunds.py` 对 10 个边界逐项核对：未支付、已取消、已退款、高金额、特殊类目、超期、部分退、运费、换货、并发 | 金额与资格**零错误**；错误即阻断 |
| S4 | 状态与恢复 | `SqliteSaver` 下重启进程、同会话并发、中断恢复 | 不丢消息、不重复执行、恢复后状态一致 |
| S5 | 渠道可行性 | 调研自营商家常用渠道（网页/企微/微信/平台 IM）的接入方式与限制 | 给出“能接/不能接/需要什么”的结论，不实现 |
| S6 | 评测可信度 | 审计 50 条评测：谁写的、覆盖什么、是否自证；补 20 条真实工单 | 能说清“这套评测能证明什么、不能证明什么” |

**S1 和 S3 是硬门槛**：一个决定“模型值不值”，一个决定“钱会不会错”。

## 7. 证据管理

建一个 `research/` 目录（可与 `docs/` 并列），核心是一张 CSV：

```csv
id,假设,来源类型,来源,原文或原话,可信度,影响决策,日期
E001,H1,访谈,受访者A（客服主管/自营商城/鞋类）,"最近一单退款我开了3个系统，花了18分钟",B,"是否做退款闭环",2026-11-05
E002,H4,实测,本地S1运行,"50条评测引用准确87%，P95 9.2s，单均¥0.06",A,"模型是否达标",2026-11-06
```

规则：

- 可信度：A=官方文档/实测/原文；B=一手访谈/截图；C=二手报道/厂商宣称。
- 每个结论至少 2 个独立来源；只有一个来源的标“待验证”。
- 访谈记录用编号，不写真实姓名；截图打码。
- 一周结束证据表 <30 行，说明调研没做够。

## 9. 决策备忘录模板（一页）

```text
决策问题：
候选方向（含“不做”）：A / B / C

每个方向：
  支持证据（编号）：
  反对证据（编号）：
  未知/待验证：

评分（1–5）：需求强度、可行性、差异化、个人可交付、证据可信度

选择：
第一版范围：做什么 / 明确不做什么
4 周内可证伪的验证：指标 + 阈值 + 数据来源
杀死条件：出现什么就停
未决问题与下一步：
```

**阈值事先写死**，例如：

- H1：8 家中 ≥5 家愿意提供 10 张脱敏工单 + 1 小时试用 → 继续。
- H2：20 条真实工单上，人工分钟数下降 ≥30%，且零金额错误 → 价值成立。
- H4：50 条 + 20 条真实工单，引用准确 ≥90%，退款边界零错误，单均成本 ≤ 目标值 → 技术成立。
- H5：P1 纵切 ≤ 4 周可演示，且能回答 10 个追问中的 8 个 → 个人可行。

阈值不要等调研结束再定，否则你会用感觉说服自己。

## 11. 常见坑（与本项目直接相关）

1. **把 mock 当真实**：22 个测试全绿、50 条评测通过，只能证明“演示链路正确”，不能证明真实模型效果。
2. **用自造评测集自证**：50 条是工程自测，不是业务标注；需要 20 条真实工单做外部校验。
3. **复现参考项目却没有差异**：如果只能讲“我实现了 MewHelp”，求职叙事会很弱；差异必须来自调研。
4. **先做生产化**：JWT、多实例、Milvus、监控都不能替代“有人愿意用”。
5. **只看平台官方客服**：自营商家的真实渠道可能是微信/企微/网页，平台客服不是唯一替代方案。
6. **把“能答”当“能解决”**：退款/换货/物流异常才是闭环；问答只是入口。
7. **忽略政策维护成本**：政策谁更新、错了谁负责，决定产品能不能持续。
8. **忽略单位经济**：模型成本、检索成本、人工兜底成本，要按“每成功解决一单”算。

## 12. 交付物与“调研完成”的定义
